# BOREAL — Camping Trip Booking Automation

مشروع برتفوليو لـ **Automation Developer**: صفحة هبوط لشركة رحلات تخييم في كندا، مع فورم حجز يرسل البيانات تلقائياً لنظام إدارة الحجوزات.

## لماذا تغيّرت فكرة المشروع؟
بدأ المشروع كـ "CRM sync" بفورم تواصل بسيط. المشكلة: الفورم البدائي لا يصلح للعرض ببرتفوليو مصمم UX.

**القرار:** بناء منتج حقيقي كامل — موقع شركة تخييم — بدل فورم مجرّد. الفائدة مزدوجة:
1. **بصرياً:** قطعة قابلة للعرض فعلاً بالبرتفوليو
2. **تقنياً:** بيانات الحجز أغنى بكثير من "اسم + إيميل + رسالة" — اختيار رحلة، عدد أشخاص، تأجير معدات، جهة اتصال طوارئ، ملاحظات صحية. هذا يجعل الأوتوميشن نفسه أذكى (حساب سعر، تحقق من المقاعد، رسالة تأكيد مخصصة).

## ⚠️ الفرق بين "تطبيق ويب" و"أوتوميشن"
هذي أهم نقطة بالمشروع، وكانت ملاحظة صحيحة أثناء البناء:

بالمرحلة الأولى كان المشروع **تطبيق ويب** — صفحة + API + قاعدة بيانات محلية + لوحة صنعتُها بنفسي. نظام مغلق على ذاته.

**الأوتوميشن هو طبقة التكامل**: أن تذهب البيانات لنظام تستخدمه الشركة فعلاً، وأن تحدث أمور بلا تدخل بشري:

| المكوّن | لماذا هو أوتوميشن |
|---|---|
| `destinations/airtable.js` | البيانات تصل نظاماً خارجياً حقيقياً — لا لوحة من صنعي |
| `pipeline.js` | التسليم يُعاد تلقائياً عند الفشل، بلا تدخل |
| `scheduler.js` | إجراءات **مبنية على الوقت** — لا أحد يضغط زراً |

الموقع مجرد **الزناد (trigger)**. الأوتوميشن ما بعده.

## طبقة الأوتوميشن

```
حجز جديد
   │
   ├─▶ يُحفظ محلياً ─────▶ ٢٠١ للعميل فوراً
   │                        (لا ينتظر أي طرف ثالث)
   │
   └─▶ pipeline.deliver()  ← غير مُنتظَر عمداً
          │
          ├─ محاولة ١ ──▶ Airtable ──▶ ✅ sent (يُحفظ recordId)
          │                    │
          │                    └─▶ ❌ فشل
          │                          │
          │            ┌─────────────┴─────────────┐
          │       خطأ ٤xx                     خطأ ٥xx / شبكة
          │      (توكن خاطئ)                    (عطل مؤقت)
          │            │                             │
          │       permanent                   إعادة محاولة متزايدة
          │       توقف فوراً                 ٥ث → ٣٠ث → ٢د → ١٠د → ٣٠د
          │            │                             │
          │            └──────▶ failed ◀─────────────┘
          │                       │
          │                       └─▶ يظهر باللوحة + زر إعادة محاولة يدوية

المجدول (كل ١٥ دقيقة)
   ├─ trip-reminder    تذكير قبل ٣ أيام من الانطلاق
   ├─ pending-chase    حجز معلّق > ٢٤ ساعة → يحتاج اتصالاً
   └─ delivery-sweep   شبكة أمان لأي شيء لم يُسلَّم
```

### قرارات هندسية بطبقة الأوتوميشن

| القرار | السبب |
|---|---|
| **التسليم غير مُنتظَر** (`deliver()` بلا `await`) | العميل يجب ألا ينتظر Airtable. عطل بطرف ثالث لا يجوز أن يحوّل حجزاً ناجحاً إلى خطأ |
| **تمييز الخطأ الدائم من المؤقت** | توكن خاطئ (٤٠١/٤٠٤) سيفشل بنفس الشكل مليون مرة — إعادة المحاولة عليه هدر. أما ٥٠٠ أو انقطاع شبكة فيستحق المحاولة |
| **تراجع أسّي (exponential backoff)** | إعادة محاولة فورية متكررة تزيد الضغط على خدمة متعثرة أصلاً |
| **حفظ `recordId`** | يضمن عدم إنشاء صف مكرر عند إعادة المحاولة |
| **`resumePending()` عند الإقلاع** | لو انهار الخادم بين "حُفظ" و"أُرسل"، الحجز لا يضيع — يُلتقط عند التشغيل التالي |
| **مهام idempotent** | كل مهمة تسجّل ما فعلته على الحجز (`jobs.reminderSentAt`)، فتشغيلها مرتين لا يرسل تذكيرين |
| **قفل التداخل** (`running`) | تشغيل يدوي أثناء تشغيل مجدول لا ينتج تنفيذاً مزدوجاً |
| **وضع dry-run** | بلا مفاتيح، النظام يعمل كاملاً ويسجّل ما *كان سيرسله* — المشروع يعمل على أي جهاز بلا حسابات |

### عيب اكتُشف أثناء الربط الفعلي: الـ dry-run كان يُحسب تسليماً
**العرض:** بعد إضافة توكن Airtable حقيقي، الحجوزات التي التُقطت *قبل* الإعداد لم تُرسل أبداً.

**السبب:** التسليم التجريبي كان يُسجَّل `status: 'sent'`، فدالة `resumePending()` تتخطاه باعتباره مُسلَّماً. النتيجة: **كل ما جُمع قبل ربط الحساب يضيع بصمت** — وهو أسوأ نوع أعطال: لا خطأ، لا سجل، بيانات مفقودة فقط.

**الحل:** التمييز بين "أُرسل فعلاً" و"أُرسل إلى العدم":
```js
const wasDryRun = state?.dryRun === true;
const nowLive   = dest.isEnabled?.() ?? true;
if (state?.status === 'sent' && !(wasDryRun && nowLive)) return;
```
الآن عند إضافة المفاتيح، كل ما التُقط بوضع dry-run يُعاد إرساله تلقائياً عند أول تشغيل.

**تحقق:** الحجز الموجود (`BRL-HQJAP4`) كان `sent (dry run)`؛ بعد الإصلاح ظهر بالسجل `[pipeline] BRL-HQJAP4 → airtable ok` وقُرئ الصف فعلياً من Airtable.

### قرار: الخادم يقدّم الموقع نفسه
بدل خادم منفصل للـ API، الخادم يقدّم `index.html` كذلك. الفائدة:
- **لا CORS إطلاقاً** — الطلبات same-origin، فلا preflight ولا إعداد `allowedOrigins`
- **أمر واحد** يشغّل كل شي
- يطابق طريقة النشر الحقيقية (خدمة واحدة على Render/Railway)

هذا يحل المشكلة التي واجهناها بنسخة n8n من جذورها بدل التحايل عليها.

## تفاصيل تنفيذ تستحق الذكر
- **كتابة ذرية:** الحفظ يتم بملف مؤقت ثم `rename`. `rename` عملية ذرية على نفس نظام الملفات، فانقطاع مفاجئ أثناء الكتابة يترك الملف السابق سليماً بدل ملف مبتور
- **طابور كتابة:** الكتابات مُسلسَلة عبر Promise chain، فطلبان متزامنان لا يفسدان الملف
- **رمز المرجع:** `BRL-` + ٦ خانات من أبجدية تستبعد `0/O/1/I` — قابل للقراءة عبر الهاتف بلا لبس، ومولّد بـ `crypto.randomBytes` لا `Math.random`
- **الإشعار fire-and-forget:** فشل إرسال إشعار **لا يجوز** أن يحوّل حجزاً ناجحاً إلى خطأ بوجه العميل
- **`fileURLToPath`:** على ويندوز `url.pathname` يرجع `/C:/Users/...` وكل استدعاءات `fs` ترفضه — الدالة الصحيحة تحل هذا
- **مقاعد حيّة بالواجهة:** الشارات تُحدَّث من `/api/availability` عند التحميل وبعد كل حجز، فالصفحة تتوقف عن عرض مقاعد محجوزة للتو

## مشاكل تقنية وحلولها

### ١. الفورم داخل النافذة لا يتمرر (bug حقيقي)
**العرض:** المحتوى يتجاوز أسفل الشاشة، ولا يمكن الوصول للحقول السفلية ولا لزر الإرسال.

**السبب الجذري:** `.sheet-bd` عنصر `flex: 1` داخل حاوية `flex-direction: column`. القيمة الافتراضية `min-height: auto` تمنع عنصر flex من الانكماش تحت حجم محتواه — فيتمدد متجاوزاً `max-height` الأب، و`overflow-y: auto` لا يُفعّل أبداً.

**تعقيد إضافي:** عنصر `<form>` يقع بين `.sheet` و`.sheet-bd`، فكان يقطع سلسلة قيد الارتفاع.

**الحل:**
```css
#regForm  { display:flex; flex-direction:column; flex:1 1 auto; min-height:0; }
.sheet-bd { overflow-y:auto; flex:1 1 auto; min-height:0; }
dialog    { position:fixed; inset:0; height:100dvh; }
dialog[open] { display:grid; place-items:center; }
```
أُضيف كذلك `overscroll-behavior: contain` (يمنع تمرير الصفحة خلف النافذة) وقفل تمرير `body` عند الفتح.

**التحقق:** قيست الأبعاد فعلياً بـ `getBoundingClientRect` بدل الاكتفاء بالنظر —
`scrollHeight` ١٣١٨px داخل نافذة `clientHeight` ٢٩٩px، والصندوق كامل داخل الشاشة، وزر الإرسال ثابت ومرئي.

### ٢. `100vh` على الموبايل
استُخدمت `dvh` (dynamic viewport height) بدل `vh` — لأن `vh` لا يحسب شريط عنوان المتصفح المتحرك على الجوال، فتُقتطع النافذة.

## النشر

منشور على **Render** (خطة مجانية). المتغيرات البيئية تُضبط من لوحة Render، ولا تُرفع أبداً مع الكود.

### مشكلة نظام الملفات المؤقت — وحلها
الخطة المجانية بـ Render تعطي نظام ملفات **مؤقتاً**: `data/bookings.json` يُمسح مع كل إعادة تشغيل أو نشر.

الخطر ليس ضياع السجلات (فهي بـ Airtable)، بل **عدّاد المقاعد**: لو بدأ الخادم بذاكرة فارغة، ستظهر الرحلات المكتملة كأن بها أماكن، ويقبل الموقع حجوزات فوق السعة.

**الحل:** Airtable هي قاعدة البيانات الدائمة، والملف المحلي نسخة عمل قابلة للاستغناء. عند الإقلاع يقرأ الخادم كل الصفوف من Airtable ويعيد بناء حالته:

```js
if (airtable.isEnabled()) {
  const added = await store.hydrate(await airtable.list());
  if (added) console.log(`[store] restored ${added} booking(s) from Airtable`);
}
```

الصفوف المسترجعة تُوسَم `sync.status = 'sent'` مع `recordId` الأصلي — فلا يُعاد إنشاء صف مكرر.

لو تعذّر الوصول لـ Airtable وقت الإقلاع، يسجّل تحذيراً ويكمل بالنسخة المحلية: البدء بحالة قديمة أفضل من عدم البدء إطلاقاً.

**تحقق:** حُذف مجلد `data` بالكامل (محاكاة إعادة نشر) →
```
[store] restored 2 booking(s) from Airtable
Berg Lake Traverse   0/10 متبقي     ← بقيت مكتملة، لم تُعَد إلى 2
```

## لماذا كود بدل n8n؟
قرار متّخذ بعد تجربة n8n فعلياً ومواجهة مشاكل تثبيت:
1. **يفرّق عن الـ no-code** — سحب nodes يقدر عليه أي أحد؛ كتابة خادم بتحقق وحماية تُظهر مهارة هندسية
2. **قابل للمراجعة** — الكود يُقرأ على GitHub، بينما `workflow.json` كتلة لا تُقرأ
3. **صفر تبعيات** — لا يتكرر جحيم التبعيات الذي أوقفنا سابقاً
4. **قابل للنشر مجاناً** برابط حيّ يوضع بالبرتفوليو
